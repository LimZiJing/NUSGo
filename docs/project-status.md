# NavUS Project Status

This document records the shared implementation status and near-term engineering direction. Stable domain and product vocabulary belongs in the root `CONTEXT.md`; agent behavior belongs in `AGENTS.md`.

## Stack

- npm workspaces: `frontend`, `backend`, and `shared`; backend and shared are minimal placeholders.
- MapLibre GL JS for map rendering
- React 19, TypeScript, and Vite in `frontend`; static JSON data in `frontend/public/data`.
- Application code and types under `frontend/src`.

The accepted route architecture uses a self-hosted Valhalla pedestrian service behind a server-side boundary and a pure planner that composes walking connections with the canonical shuttle network. OSRM and other routing engines remain replaceable alternatives behind that boundary. Other potential future tools include `ngraph.graph`/`ngraph.path` for a client-side routing prototype, `@turf/turf` for spatial calculations, `ical.js` for calendar import, and PostgreSQL/PostGIS behind a future API.

- Map attribution remains visible as a small, readable footer without the expanded disclosure control, preserving the OpenFreeMap and OpenStreetMap credits on mobile and desktop.
- Map tile error reporting and MapLibre navigation controls.
- Venue data loaded from `frontend/public/data/venues.json`.

- Venue selection opens the venue-first Explore view, flies to the venue, and shows a selected venue marker without a duplicate map popup.
- The shared desktop and mobile venue-details panel uses the venue code as its heading, followed by the room name and confirmed floor/building metadata, a Navigate action, a NUSMods link, and up to three nearby validated NUS shuttle stops within 500 m. Coordinates remain internal for navigation and nearby-stop lookup but are not shown in the panel. Stop rows use canonical route colors and open the existing stop popup while preserving the venue-details return path. Navigate sets the destination and, when an active valid fix exists, atomically replaces the origin with a frozen Current location endpoint; without an active fix it preserves the existing origin and requests no location permission. It opens the partial Plan sheet on mobile. Mobile shuttle browsing uses canonical route chips and a single ordered-stop timeline; the Explore return control clears the active map route while retaining the chosen route for reopening.
- Enabled non-selected buttons and the NUSMods action darken by 15% on hover. Selected shuttle route chips and the current mobile tab keep their active appearance; unselected route chips darken on hover.
- Trip endpoint controls let users choose stable venue or shuttle-stop origins and destinations, swap or clear them, and show distinct endpoint markers.
- Plan endpoint selection is separate from Journey calculation: the responsive Plan panel exposes an accessible `Get route` action, endpoint changes cancel and clear the current Journey and map route, and resource loading does not start planning without an explicit submission. The Origin control also has an explicit browser-location action that finds the nearest mapped venue, keeps the existing origin until success, and exposes retryable failure feedback.
- Plan endpoint controls and Journey details use a compact responsive layout with 36px minimum controls, consistent endpoint and action alignment, left-aligned validation, and right-aligned actions across desktop and mobile light and dark themes. Primary text sizes and endpoint, search, swap, clear, current-location, and `Get route` workflows remain unchanged.
- Shuttle-stop popups can assign a stop directly as a trip origin or destination.
- In the mobile Stops tab, selecting a stop opens its detail sheet and focuses a neutral map pin above the sheet without a popup. Entering Stops also closes an Explore stop popup. The pin sits above the still-visible stop marker and uses the same zoom as venue selection. It remains selected after Back, is shown only in Stops, and returns without moving the camera after a tab switch; Explore retains its stop popups.
- The mobile Stops overview shows every map-centred stop in the Nearby list and a browser-saved Favourites list. Nearby requests device location on entry and always orders stops from nearest to farthest from the visible map centre. A successful location action automatically opens timing rows only for stops within 200 m of the location; all other timing rows remain closed, and Favourites remain closed unless opened manually. Distance badges show device distance only when a fix is available. The expanded Stops sheet fills its 50% viewport-height allowance even when few stops are listed. Its grab handle, selector, and location notice stay above the independently scrolling card list; focused-stop details scroll below the fixed handle. Tapping a title bar animates its timing rows open or closed, while tapping its star changes its favourite state. The card animation respects reduced-motion settings and keeps closed route controls out of keyboard focus. Multiple reusable cards retain their expansion state across tab changes; both card and focused-sheet stars edit the same favourites. Map markers open the focused stop sheet. Visible Stops and Journey planning now read the shared backend snapshot through one browser arrivals client, apply new snapshot generations together, ignore older responses, debounce rapid map stop-set changes, count down from per-stop observation times, and keep the last snapshot visible during refresh or retry for the same visible stop set; snapshots are cleared when the visible stop set changes. Fresh internal or mapped public arrivals receive the LIVE badge; recently observed arrivals may remain visible without LIVE during refresh or retry within the 120-second maximum age boundary, while expired, unavailable, and no-arrival states are shown without placeholder internal timings. When live arrivals are empty, Stops uses route service windows to show compact scheduled or ended states; first-service countdowns are shown within a 30-minute grace period. Public service tokens remain outside the live internal-route mapping.
- Stops bus-route rows show up to three downstream favourited stop nicknames for each internal route, using the route's ordered stop list. Public-service rows display server-side LTA DataMall arrival timings and distinguish live, no-estimate, out-of-operation, and provider-error states. Public buses are display-only and are not used by Journey routing. The matching is forward-only, uses stable stop IDs, excludes transfers and the selected stop, and does not wrap a route's closing terminal back to its first stop.
- Shuttle-stop data loaded from the bundled `frontend/public/data/shuttle-network.json` model.
- Shuttle stops rendered as neutral transit-ring markers with collision-aware short-name labels from zoom 14 onward; selected-route content remains full opacity, while inactive stops and labels fade to 20% from zoom 14 onward, and open-stop content remains visible below that threshold.
- Venue markers use neutral map pins.
- Validated route lines are neutral and subdued in the all-routes state, with official route colors reserved for the selected route.
- The transit model contains 8 internal shuttle routes, 33 stops, service associations, and ordered stop IDs.
- Transit model references are validated before shuttle markers are rendered.
- MapLibre lifecycle, basemap presentation, transit layers, venue markers, shuttle-stop markers/popups, and trip endpoint markers are composed from focused adapters under `frontend/src/infrastructure/map/`; the application consumes the framework-free MapSession contract under `frontend/src/app/contracts/`.
- `frontend/src/app/navigation-session.ts` now owns application state and commands for loaded venue/transit data, Explore view history, route selection, trip endpoints, resource status, startup/map errors, and map coordination; endpoint search queries remain local to the trip-endpoint feature seam, and `frontend/src/app/app.tsx` is reduced to composition and the React external-store adapter.
- JSON fetching and validated resource loaders are organized in `frontend/src/infrastructure/data/`.
- The transit loader returns one immutable canonical network through `index.network`; network and route geometry fetches start in parallel and are validated deterministically.
- Pure transit, venue, location, trip, and Explore view models are owned by `frontend/src/domain/`.
- Local browser location tracking starts from a one-tap target control and focuses the map on the first available fix. The map shows a distinct blue target marker. Valid browser fixes are accepted regardless of reported accuracy, and location fixes stay in browser memory rather than being sent to NavUS services. Navigate from venue or stop details captures an active valid fix as a frozen Current location origin; subsequent device updates move only the blue target marker, while Journey planning, the green origin marker, endpoint labels, and map reset use the captured coordinates.
- Mobile location uses one accessible target button at the top-left safe area, stays above the mobile sheets, and is hidden while Plan is expanded. It keeps the location-control action, focusing the latest active fix or the first fix received after permission. When no active fix is available, it centers on Kent Ridge MRT at zoom 15 before requesting or retrying location. Location updates never move the camera on their own.
- Issue #39 automated checks cover resource validation, immutable indexes, loader failure isolation, and the checked-in transit manifest. The canonical release smoke checklist is in `docs/qa/manual-smoke-check.md`; the 2026-09-21 browser pass is recorded as passed with limitations because exact release and mobile viewports were unavailable.
- Build-generated shuttle timing estimates use the canonical route geometry, are validated against the route and stop model, and are loaded through `loadShuttleTimingData`. Live stop arrivals use a cached server-side NUS adapter when configured, while static ride estimates remain the fallback. When available, route service-hour windows are checked in Singapore local time so after-hours routes are not treated as zero-wait options.
- The pure `planJourney` module compares a direct walking connection with directed single-shuttle rides. Each venue endpoint contributes up to three reachable walking connectors selected by Valhalla duration, with no five-minute cutoff; a user-selected stop stays fixed. The planner does not create transfers or reboardings. Its `zeroShuttleWaitingTime` policy remains the fallback when live waiting data is unavailable. Navigation-session state publishes the selected Journey, MapSession renders its walking and shuttle geometry with replacement and disposal cleanup, and shuttle stops are highlighted only from each shuttle leg’s boarding stop through its alighting stop in the Route’s official color. The responsive Plan trip panel presents the single Recommended Journey with a compact dot-and-line timeline, ordered endpoints and leg details, estimate notices, and failure states.
- Walking planning loads the validated directed graph for the 33 canonical shuttle stops and runs origin-to-network and network-to-destination matrix queries in parallel. The application ranks direct walking against the available one-shuttle candidates, enriches selected walking legs with Valhalla route geometry, and yields between cancellable candidate-search batches. An `exact` result exhausts this supported candidate set; it does not establish a global optimum across transfers or stops outside the selected connectors. A budgeted result remains a valid Recommended journey and may have a faster candidate within the supported set.
- The Journey planner uses a priority queue, preserves time-dependent labels with different arrival times, removes only labels dominated at the same timing context, and rejects repeated planning states within a path so walking cycles cannot prevent termination. Browser planning is cancellable and yields between search batches so the page remains responsive. A search that finishes within its budget is marked exact; a budgeted result remains a valid Recommended journey but may not be the globally fastest route.
- Development previews include a Journey test-time overlay for a frozen Singapore date and time. In this mode the Journey planner skips live arrivals, uses a clearly labelled five-minute wait per shuttle boarding, and still checks each boarding against route service windows. The choice resets on reload; production builds and the Stops live-timing display are unaffected.
- Desktop widths from 769px use one persistent left navigation column with shared Explore, Stops, and Plan views; mobile keeps the bottom tab bar and bottom sheets. Stops is the default view, desktop Stops loads live arrivals and service windows only while active, and the map reserves the measured column width as its left viewport inset. The shared navigation keeps inactive views mounted and inert so view state survives switches and breakpoint changes.
- Mobile widths up to 768px use persistent Explore, Stops, and Plan tabs over the shared map. Stops opens first; each tab starts at a partial sheet whose height plus the occupied navigation inset is capped at 60% of the visual viewport, with a nominal 200px sheet minimum when space allows. Each tab remembers its own detent. Collapsed sheets keep a 44px-high shell with a 5px grab bar and touch strip above bottom navigation; tapping the strip reopens the last non-collapsed detent. Meaningful drags follow the pointer without resistance: from partial, a 24px upward or downward drag settles to full or collapsed; from collapsed, a 24px upward drag settles to partial. From full, a 24px downward drag settles to partial; a release below 30% of the visual viewport settles to collapsed. Sub-threshold movement returns to the starting detent, and taps retain the button's detent cycle. Tab buttons are at least 36px high. Full-height sheets fill the available area above the always-visible, usable navigation pill. Search focus opens the full-height sheet and search results return to partial; cancellation or Escape restores the previous detent unless manually changed. Safe-area and visual-viewport sizing, independent sheet scrolling, reduced-motion handling, and non-modal focus behavior support the shared workflows. In Explore's shuttle view, the segmented selector and shuttle route chips stay fixed while only the ordered stop list scrolls. Shuttle routes presents chips and an ordered-stop timeline in one sheet. Mobile venue details use a ghost return button whose label follows the previous view; the button remains reusable for future flows. Issues #119–#120 are complete prerequisites for the remaining mobile polish.
- Native scroll areas share a reusable `ScrollArea` UI primitive and an app-wide thin, rounded, arrowless scrollbar style, with colors that adapt to light and dark themes. Vertical and horizontal scroll regions retain their local sizing and overflow bounds.
- Shuttle route chips use the common-use order A1, A2, D1, D2, R1, R2, K, P. Their scrollbar is hidden while overflow is indicated with subtle edge fades and text-only directional chevrons; touch, pointer drag, trackpad, wheel, and keyboard scrolling remain available, and selecting a route keeps its chip visible.
- The shared UI style entrypoint loads semantic theme tokens plus light and dark theme value files under `frontend/src/ui/styles/themes/`. Shared panels, controls, route browsing, responsive sheets, and status styles use those tokens for colors, repeated radii, shadows, and control heights. Theme tests check key text and status contrast in both themes. A simple Light/Dark button switches the active theme for the current page; reload returns to the system theme. OS-driven light values preserve the current appearance, while official shuttle route colors remain outside the theme contract. The selected-stop fallback also uses a theme token.
- Grab-bar taps and mobile tab or Explore view switches animate between their measured sheet heights; view switches also fade in the incoming content. Drag releases settle to the direction target, with a full-start downward release below 30% collapsing the sheet; settling uses a brief bounce and respects reduced-motion settings.

## Current limitations

- `frontend/public/data/bus-routes.json` is the original route-name source; the app now consumes the normalized `shuttle-network.json` model.
- The checked-in model contains reviewed ordered stop IDs and bundled road-following GeoJSON route geometry; targeted release smoke evidence exists at 1280 × 720, while exact release/mobile viewports and failure injection still need manual verification.
- Accurate transit behavior depends on the checked-in network, geometry, and verification manifest remaining in sync; CI validates that integrity gate.
- The accepted Journey architecture is documented in [ADR 0002](adr/0002-nus-route-recommendation-architecture.md), with the timing policy recorded in [Shuttle timing policy](shuttle-timing.md). The Valhalla walking route-engine boundary and pure Journey planner are now connected through the navigation session; the app still needs a configured self-hosted Valhalla endpoint for usable walking results. The checked-in walking stop graph must be regenerated when the canonical stop model, walking profile, or routing data changes. Shuttle ride estimates, live waiting estimates, service-window checks, and the live-data failure distinction are implemented; live data still depends on server-side NUS credentials, and a valid no-bus response removes shuttle options while provider failures surface as planning errors. Live browser planning favours a predictable response and page responsiveness; when the bounded search cannot prove the global optimum, the UI presents the valid result as recommended rather than fastest.
- NUSMods is useful for venue/stop associations and bus-arrival integration, but its current NextBus client does not provide route geometry. Live-arrival reliability also needs separate verification.
- The OpenFreeMap basemap is suitable for the prototype. NUS-specific paths, entrances, covered walkways, and indoor connections may require custom GeoJSON or another licensed data source.
- Location tracking depends on browser permission and device accuracy. It does not replace chosen trip endpoints, replan journeys, or continue after the app closes.
